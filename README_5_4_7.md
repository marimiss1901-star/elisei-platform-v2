# ELISEI 5.4.7 — Memory-Safe WB Sync

Патч исправляет падение backend Render по памяти (512 МБ) во время загрузки финансовых отчётов WB, хранения, приёмки и эквайринга.

## Что изменено

- Финансовая детализация и эквайринг загружаются страницами, по умолчанию по 2500 строк.
- Каждая страница сразу сохраняется в PostgreSQL пакетами по 250 строк.
- Полный отчёт больше не удерживается в RAM и не дублируется в snapshot/общем JSON.
- Сырые строки хранятся в `wb_stream_items`.
- После завершения создаётся компактный итог по товару и схеме FBS/FBO для аналитики и Эла.
- Платное хранение разбито на интервалы по 2 дня, приёмка — по 7 дней.
- Тяжёлые этапы не выполняются параллельно.
- Курсор `rrdId`, `syncId`, номер страницы и число сохранённых строк записываются в `wb_sync_states.metadata`.
- После перезапуска Render синхронизация продолжается. Повтор страницы безопасен: строки записываются через upsert и не дублируются.
- Предыдущий успешно загруженный отчёт остаётся доступным до полного завершения нового.

## Установка

Загрузить содержимое архива в корень репозитория с заменой файлов.

Render backend:

- Root Directory: `backend`
- Build Command: `npm install`
- Start Command: `npm start`

Затем выполнить `Manual Deploy → Clear build cache & deploy`.

Frontend обновлять не требуется.

## Необязательные настройки

Значения по умолчанию рассчитаны на Render 512 МБ:

```env
WB_HEAVY_PAGE_LIMIT=2500
WB_HEAVY_DB_BATCH_SIZE=250
WB_HEAVY_STAGE_COOLDOWN_MS=65000
```

При повторном превышении памяти можно уменьшить `WB_HEAVY_PAGE_LIMIT` до `1000`. Увеличивать выше `5000` код не позволит.

## Проверка

После deploy открыть «Синхронизации» и один раз нажать «Запустить доступные этапы». Финансы могут показывать статус «В очереди» между страницами — это штатно. Не нужно нажимать кнопку повторно.

Патч проверен синтаксически и unit-тестами пакетной записи/финансовой агрегации. Живой вызов WB API не выполнялся, поскольку токен пользователя не передавался в среду сборки.
