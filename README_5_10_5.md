# ELISEI 5.10.5 — Smart WB Scheduler

Релиз устраняет стартовый «залп» запросов к Wildberries и переводит синхронизацию на приоритетную очередь.

## Что изменилось

1. **Один due-этап на кабинет за цикл worker.** Одновременно разные фоновые lanes больше не запускают несколько методов от имени одного продавца.
2. **Приоритеты.** Сначала каталог и оперативные данные: товары → заказы → продажи → остатки → финансы → реклама. Исторический FBS-архив имеет низкий приоритет.
3. **Незавершённые отчёты важнее новых запросов.** Если WB уже выдал taskId, планировщик сначала завершает/проверяет этот отчёт.
4. **Cold start без burst.** При первом подключении этапы получают разнесённые `nextAllowedAt`, а не одну и ту же секунду.
5. **Rate-limit headers.** ELISEI учитывает `X-Ratelimit-Remaining`, `X-Ratelimit-Reset`, `X-Ratelimit-Retry` и `Retry-After`. Если окно ещё закрыто, новый запрос не отправляется.
6. **Короткие интервалы.** Окна до 3 секунд можно дождаться внутри текущего этапа; длинные интервалы сохраняются в PostgreSQL и продолжаются фоновым worker.
7. **Без ложной ошибки.** Ожидание лимита теперь серое/нейтральное состояние с иконкой часов: «Ожидает окно WB». Реальная ошибка остаётся красной.

## Что не меняется

- настоящий `429` WB не обходится и не сбрасывается;
- finance Base продолжает соблюдать фактический `nextAllowedAt`;
- частичные финансовые строки, `rrdId`, taskId, cursors и история синхронизации сохраняются;
- пользователю по-прежнему нужен один WB-ключ.

## После установки

1. Заменить файлы патча поверх 5.10.4.
2. Передеплоить backend и frontend.
3. `/health` должен показать backend `2.22.5`.
4. Не нажимать «обновить всё» несколько раз: открыть «Синхронизации» и дать Smart Scheduler самому продолжить очередь.
5. Существующие настоящие WB-лимиты не исчезнут мгновенно; после их окончания следующий этап запустится автоматически.
