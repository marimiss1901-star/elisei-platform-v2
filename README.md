# ELISEI 5.11.2

ELISEI — отдельная SaaS-платформа для продавцов маркетплейсов. MAXADORRE не входит в этот репозиторий: базы, токены, окружения и клиентские данные проектов не смешиваются.

## Версии

- Frontend: `5.11.2`
- Backend: `2.23.2`
- Ядро Эла: `5.11.2`

## Архитектура интеграции WB

```text
WB API
  ↓
неизменённый JSON-снимок
  ↓
строгий адаптер конкретного метода
  ↓
единая карточка товара
  ↓
PostgreSQL
  ↓
рабочие разделы ELISEI
```

Модули интеграции находятся в `backend/src/wb/`:

- `adapters/catalog.js` — карточки, размеры и ШК;
- `adapters/warehouse-remains.js` — официальный отчёт остатков и сверка сумм;
- `adapters/promotion.js` — кампании и статистика продвижения;
- `identity.js` — безопасное сопоставление идентификаторов;
- `product-master.js` — единая карточка товара;
- `snapshot-store.js` — исходные/нормализованные снимки и checksum.
- `api-policy.js` — блокировка устаревших endpoint и безопасная политика СГТ-складов;
- `smart-scheduler.js` — приоритетная очередь WB, распределение cold-start запросов и спокойные статусы ожидания API-окон;
- `fbs-archive.js` — план месяцев, курсорная пагинация и стабильные ключи архива FBS.







## Корректные лимиты финансов WB 5.10.4

- Исправлена неверная трактовка лимита `POST /api/finance/v1/sales-reports/detailed`: Базовый токен без сервисного секрета имеет лимит 2 запроса в 24 часа с интервалом 12 часов; Service / Personal / Base + service secret работают в быстром режиме около 1 запроса в минуту.
- ELISEI больше не сбрасывает законный длинный `queued/rate_limited` таймер финансов.
- Размер страницы финансов увеличен с 10 000 до максимально разрешённых 100 000 строк, чтобы на Базовом токене за один разрешённый запрос получать максимум данных.
- Для документов исправлен режим Base без secret: длинный лимит WB больше не маскируется коротким локальным cooldown.
- Интерфейс прямо объясняет, когда задержка вызвана лимитом Базового токена, и подчёркивает, что второй пользовательский токен не нужен: быстрый режим достигается сервисным секретом ELISEI на backend после регистрации сервиса.

## Порядок обновления

1. Загрузить файлы релиза в репозиторий ELISEI с заменой.
2. Backend: **Manual Deploy → Clear build cache & deploy**.
3. Проверить `/health`: backend должен запуститься, `database` — `ok`.

## ELISEI 5.10.5 — Smart WB Scheduler

- один приоритетный due-этап на кабинет за цикл фонового worker;
- первая синхронизация распределяется по времени вместо одновременного запуска десятков методов;
- уже созданные WB report/task получают приоритет на завершение;
- `X-Ratelimit-Remaining`, `X-Ratelimit-Reset`, `X-Ratelimit-Retry` и `Retry-After` используются как фактические окна API;
- короткое окно до 3 секунд ожидается внутри текущего этапа, длинное возвращается в очередь без запроса;
- реальный `429` остаётся `rate_limited`, локальное ожидание планировщика остаётся `queued`;
- UI различает «Ожидает запуска», «Ожидает окно WB», «Загружается», «Частично» и реальную ошибку.

## ELISEI 5.11.2 — SKU 360: единый язык состояний

- Статусы внутри SKU 360 больше не противоречат верхнему покрытию: `partial` отображается как «Пока нет в загруженной части»/«предварительно», `waiting` как «Ожидается», `ready` без строк как подтверждённое отсутствие, а не как незагруженные данные.
- Верхняя строка прямо сообщает количество внутренних потоков, поэтому число источников не путается с шестью укрупнёнными доменами.
- Для экономики backend отдаёт readiness каждого показателя отдельно: выручка, к перечислению, комиссия, логистика, хранение, приёмка, эквайринг, реклама, штрафы, налоги и общие расходы.
- Подтверждённый ноль сохраняется нулём. Ноль из частичного потока остаётся скрытым.
- Частичные остатки объясняются отдельно по FBS/FBO.
- Пустые блоки рекламы, поиска, отзывов, остатков и финансов используют разные тексты для `ready`, `partial` и `waiting`.

## ELISEI 5.11.1 — SKU 360: доверие к данным

- Пока `/product-360` ещё загружается, экран больше не подставляет нули из строки общей таблицы товара.
- Для каждого домена SKU 360 есть состояние `ready / partial / waiting / missing`.
- Нулевое значение из частичного потока не считается подтверждённым нулём и скрывается до завершения потока.
- Частичные ненулевые значения можно показывать как предварительные.
- Продажи, финансы, реклама, FBS/FBO-остатки, поиск, отзывы, вопросы и история остатков оцениваются отдельно.
- Если данных недостаточно, блок «Что делать первым» говорит, что данные собираются, а не объявляет отсутствие проблем.
- SKU 360 автоматически обновляется при изменении состояния фоновых синхронизаций, без закрытия карточки товара.

## ELISEI 5.11.0 — SKU 360

- контекстный «рентген» товара открывается по клику из Товаров, Аналитики, Остатков, Финансов и Цен;
- в одном экране объединены продажи, выручка, операционная прибыль, расходы WB, реклама, поисковые запросы, остатки, отзывы, вопросы, возвраты и ценовой коридор;
- сопоставление потоков строгое: `nmID → barcode → vendorCode → chrtID`; название товара никогда не используется как ключ;
- SKU 360 показывает покрытие источников и не подменяет отсутствующие данные нулями;
- блок «Что делать первым» выводит приоритетный сигнал по подтверждённым данным;
- отдельной вкладки в левом меню нет: SKU 360 остаётся контекстным слоем поверх рабочего раздела.


## ELISEI 5.11.3 — SKU 360 Fast Open

- SKU 360 открывается прогрессивно: сначала быстрый core, затем фоновое full-обогащение.
- Smart WB Scheduler больше не отменяет запрос SKU 360 из-за изменения `nextAllowedAt/status`.
- Расширенный поиск товара в `wb_stream_items` переведён с повторных `payload::text ILIKE + COUNT` на один точный проход по nmID/barcode/vendorCode/chrtID.
- Если расширенное обогащение не успело, уже загруженная карточка остаётся доступной и честно помечает детализацию как ожидающую.


## ELISEI 5.11.4 — SKU 360 Data Isolation

- строгая изоляция поисковых фраз и рекламы по SKU;
- search overview/group строки не показываются внутри SKU 360;
- реклама привязывается только по точному nmID;
- batch поисковых запросов WB ограничен 20 nmIds.
